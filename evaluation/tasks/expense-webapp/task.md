# タスク: expense-webapp（経費申請 Web アプリ・2ステージ）

主戦場 A/B の第2測定タスク（audits/PROPOSALS.md A4-3）。ハーネスの価値仮説
「曖昧要件・複数機能・変更要求・回帰リスクのある課題で成功率と保守性が上がる」を
検証する。todo-cli（小規模・明確要件）とは対照的に、memo は**意図的に曖昧**で、
締め日ルールに矛盾を1つ仕込んである（「月末締め」と「25日締め」が別の行に混在）。

- harness アームは /00 の要件ヒアリングで矛盾を検出し、ユーザー回答で解消して
  その決定を文書に記録するはず
- bare アームには解消情報を与えない（発話は継続督促のみ）。bare が合格するには
  自力で矛盾に気づき、どちらかに決めて記録する必要がある
  （チェッカーは 25日/月末どちらの決定でも「記録があること」だけを見る）

さらに**第2ステージ（変更要求）**を持つ: 第1ステージの完成後、
「承認済み申請の金額修正は差戻しでなく修正履歴つきの直接編集にしたい」という
運用中の変更依頼を投入する。既存機能（承認フロー・月次集計）への回帰リスクが
ある変更であり、harness アームは /12-change-request の差分駆動・再ゲートで、
bare アームは素の会話で対応する。

発話系列のステージ境界は `===` だけの行で表す（`---` は発話区切り、
`===` はステージ区切り。`tools/e2e-run.py` がステージ終端ごとに
`check.py --stage <n>` を実行して中間結果を記録する）。

## memo（両アーム共通の入力）

```memo
# 要件メモ（経費精算の件）

うちのチーム（7人）用に、経費申請を管理する簡単な Web アプリが欲しい。
今は Excel を回覧していて、誰がどこまで承認したか分からなくなる。

- メンバーが経費を申請できる（日付・金額・カテゴリ・メモくらい）
- 申請は後から直せるようにしてほしい。間違いも多いので削除もできること
- 承認は上長がやる。承認したかどうか申請者に分かるように
- 却下もある。却下されたら直して出し直すことがある
- 月ごとの集計が見たい。誰がいくら使ったか、カテゴリ別も見たい
- 経費は月末締めで、翌月にまとめて精算している
- 通知はメールか何かで来ると嬉しい（必須ではない。あれば）
- 毎月25日締めなので、25日までに出た申請はその月の集計に入れてほしい
- 社内の PC ですぐ動かしたい。インストール作業はしたくないので、
  Python が入っていればそのまま動くこと（標準ライブラリのみ、pip 不可）
- データはファイル保存でよい（DB のインストールは不可）
- 同時に使うのは数人程度。ログイン機能はなくてよいが、誰の申請かは分かるように
- テストを書いて全部通しておくこと
```

## 受入条件（check.py がコード化している内容）

チェッカーは「生成物」だけを対象にする: workdir が git リポジトリなら
bootstrap コミット以降に追加・変更されたファイルのみを走査する
（harness アーム同梱のハーネス文書や memo 自体を誤検出しないため）。
実装方式の多様性（ファイル名・構成の違い）に頑健であるよう、
特定のファイル名やエンドポイントは決め打ちしない。

第1ステージ（`--stage 1`）:

1. 生成物に Python ソースが存在する
2. 申請 CRUD（作成・一覧）・承認遷移・月次集計の実装痕跡がソースにある
3. テストスイート（`test_*.py` / `*_test.py`）が存在し、全件成功する
4. **矛盾解消の痕跡**: 生成された文書またはコードコメントに、締め日を
   どちらかに決めた記録がある（25日でも月末でもよい。決定の記録が要る）
5. 補助観測（合否に含めない）: README 等から起動方法を発見してサーバを起動し、
   HTTP 応答が返るか（web が動かない実装でも 1〜4 を満たせば合格 =
   テストスイート実行+コード構造検査へのフォールバック）

第2ステージ（`--stage 2`）: 上記 1〜4 の**再検証（回帰）**に加えて:

6. 修正履歴つき直接編集の実装痕跡がソースにある
7. テストが更新されている（履歴・編集に言及するテストが存在する）

## scripted-replies（harness アーム）

第1ステージは todo-cli（D049 実測文言）と同じ骨格。2発話目はヒアリングへの
回答で、締め日矛盾の解消・通知スコープ外・権限の簡易運用を与える
（bare には与えない。矛盾**検出**の有無は発話1の応答記録で観測する）。

`# expect: <条件>` はその発話を送る前に満たされているべき GATE_STATUS の到達状態
（装置 v2・EV-8。todo-cli/task.md の説明と同じ。未達なら督促 `kind=nudge` を上限回数まで
送り、なお未達でも台本は続行する。bare には同数の継続発話が与えられる）。第2ステージ
（/12 変更請求）は再ゲートの状態遷移が経路依存のため条件を置かない。

```scripted-replies
/00-start-project
---
ヒアリングに回答します。
- 締め日: メモに「月末締め」と「25日締め」が混在していますが、正しくは毎月25日締めです。25日に統一し、その解消の経緯を要件文書に記録してください
- 通知（メール等）: 今回のスコープ外とします
- 権限: ログインは不要です。申請時に申請者名を入力し、承認操作は承認者として誰でも実行できる簡易運用で構いません
その他は仮置き案どおりで OK です。そのまま進めてください。
---
# expect: requirements=in_progress|pending_approval|done
要件を承認します。ゲートを通過して次のフェーズへ進んでください。
---
設計はすべて提案どおりでOKです。確定してください。
---
設計を承認します。次のフェーズへ進んでください。
---
# expect: requirements=done, design=done
/05-implementation-plan
---
実装計画を承認します。/06 で実装を開始してください。
---
# expect: implementation=in_progress|done
/06-implement-task
---
続きをお願いします。テスト・リリースまで進めてください。タグ付けなど人手が必要な操作はコマンド提示だけで構いません。完了したら状況を報告してください。
===
/12-change-request 運用開始後の変更依頼です。承認済み申請の金額を直したいとき、今は差戻ししかありませんが、差戻しではなく「修正履歴つきの直接編集」にしてください。誰がいつ・いくらからいくらへ変えたかが残るようにしたいです。
---
変更を承認します。既存の承認フローと月次集計が壊れていないことをテストで確認し、テストも更新してください。
---
続きをお願いします。完了したら変更内容と回帰確認の結果を報告してください。
```
