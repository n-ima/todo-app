# 非機能要件（NFR）

根拠は `requirements/questionnaire.md` の Q-ID。「暫定値」と書いた値は質問票で聞いておらず、requirements.md §7 A-007 で確認する。

| ID | 区分 | 要件 | 目標値・基準 | 備考 |
|---|---|---|---|---|
| NFR-001 | 性能 | レスポンスタイム | 同時 10 人が使い、タスクが 15,000 件ある状態で、(1) 一覧・カレンダーの表示は 95 パーセンタイルで 1 秒以内、(2) 保存操作（タスク・メモの保存、ロック取得・解放）は 95 パーセンタイルで 500ms 以内 | Q-04-2。件数は A-006（年 5,000 件 × 3 年）。社内 LAN 内のブラウザから計測する。テストフェーズで負荷をかけて実測する |
| NFR-002 | 性能 | 同時アクセス数 | 同時利用者 10 人で NFR-001 を満たす。登録利用者数の上限は設けないが、30 人までで NFR-001 を満たす設計にする | Q-04-1。30 人は成長の余裕（暫定値） |
| NFR-003 | 可用性 | 稼働率目標 | 平日 9:00〜18:00（日本時間。暫定値＝A-007）に使えること。夜間・休日はサーバー（Windows 11）の電源を切る運用で、停止は許容する（Q-09-14）。バックアップと日次処理はその日最初のアプリ起動時に行う（US-019）。計画外停止からの復旧目標は NFR-004 に一本化する。更新のための計画停止は 1 回 30 分以内とし、事前に利用者へ知らせ、始業前または終業後のサーバーが動いている時間帯に行う（Q-04-8。夜間はサーバーが止まっているため） | Q-04-7・Q-04-8。稼働率の数値目標（%）は置かない（冗長化しない。月 0 円の制約。NFR-012） |
| NFR-004 | 可用性 | 障害時の復旧目標(RTO/RPO) | RTO: (1) ソフトウェア障害・データ破損・操作ミス: 障害の発見から 1 営業日以内（業務時間中に発見したら当日中を目標）。(2) 機材喪失（サーバー故障）: 代替機の用意は RTO の対象外とし、代替機が用意できてから 1 営業日以内（セットアップ → 復旧。US-020）。RPO: サーバーを最後に動かした日 1 日分の入力（その日最初の起動時のバックアップの時点まで戻る）。休日をはさむと、暦日では最大で連休の日数＋1 日前まで戻る（A-021） | Q-04-9・Q-04-10・A-018。復旧は復旧スクリプト（requirements.md US-020）で行う。(2) にはパスワード管理ツールに保管した暗号化鍵の控え（Q-10-7）が必要 |
| NFR-005 | セキュリティ | 認証・認可方式 | (1) 認証: アプリ自身が管理するログイン ID とパスワード（Q-03-25）。パスワードは復元できない形（ソルト付きの低速ハッシュ。方式は設計で決定）で保存し、平文で保存・ログ出力しない。パスワードは 8 文字以上（暫定値）。初回ログイン時に変更を強制する。同一 ID で 5 回連続失敗したら 15 分ログイン不可（暫定値）。8 時間無操作でセッション失効（暫定値）。(2) 認可: ロールは管理者・一般利用者の 2 種類（Q-02-2。リーダー役は管理者ロール＝Q-03-32）。全員が全タスクを閲覧でき、編集は担当者と管理者だけ、担当者未設定のタスクは全員が編集できる（Q-03-27・Q-03-31。権限表は requirements.md §5.0）。認可は画面表示だけでなくサーバー側の全 API で判定する。(3) 到達範囲: 社内 LAN からのみ（Q-09-2） | 暫定値は A-007 |
| NFR-006 | セキュリティ | データ保護（暗号化等） | (1) 通信: 社内ホスト名＋自己署名証明書の HTTPS で暗号化する。HTTP で来たアクセスは HTTPS へ転送する（Q-09-3）。(2) 保存データ: データベースファイルはアプリの実行アカウントと管理者だけが読める OS 権限にする。(3) バックアップ: 暗号化してから別サーバーの共有フォルダへ置く（Q-10-5）。暗号化鍵の控えはパスワード管理ツールに人が保管する（Q-10-7）。(4) 外部送信: アプリはデータを社外へ送信しない（外部 API・メール・解析タグ・外部 CDN 読み込みを含む）。(5) CSV 書き出しはログイン済み利用者だけが行える | データに社外秘・機密を含む可能性がある（Q-04-4）。個人情報は利用者の氏名（表示名）とログイン ID に限る |
| NFR-007 | セキュリティ | OWASP Top10相当の考慮 | OWASP Top 10 相当の対策を設計フェーズで決定し、architecture.md のセキュリティ節に記載する。要件として最低限求めるもの: (1) メモの Markdown プレビューで HTML・スクリプトを実行させない（XSS。US-009）、(2) 状態を変える全リクエストに CSRF 対策、(3) SQL インジェクション対策、(4) 認可のサーバー側判定（NFR-005）、(5) CSV インジェクション対策（US-018）、(6) リリース前に `release-security-review` スキルで監査する | 対策の具体的な方式は設計フェーズで決定（質問票冒頭で明記済み） |
| NFR-008 | 運用・監視 | ログ・監視方針 | (1) アプリのエラーログ（例外・バックアップ失敗・起動失敗）をサーバー上のファイルに 90 日分残し、それより古いものは自動で消す（Q-04-11）。(2) ログにパスワード・セッション ID を出力しない。(3) 自動の障害検知・アラート通知は作らない。障害は利用者が気づいて管理者に伝える。代わりに管理画面に最終バックアップの成否を表示する（US-020）。(4) 業務上の変更履歴（状態・担当・ロック強制解除）はアプリのデータとして保持し、タスク詳細で見られる（US-017。削除しない） | Q-04-11・Q-03-24 |
| NFR-009 | 運用・監視 | バックアップ方針 | (1) 毎日 1 回、その日最初のアプリ起動時に自動でバックアップする（Q-10-3・Q-09-14。前日の終業時点までの入力を含む）。(2) 保存先は社内の別サーバーのバックアップ用共有フォルダ、暗号化して置く（Q-10-5）。(3) 7 世代（約 7 稼働日分）を残し、古いものから自動で消す。失敗時は古い世代を消さない（Q-10-6）。(4) 更新スクリプトは入れ替えの直前にもバックアップを取る（US-022）。(5) 復旧はスクリプトで行い、実行前に確認を求め、置き換え前のデータを退避する（Q-10-4）。(6) 誤削除はまずゴミ箱（30 日）で戻し、バックアップは最後の砦とする（Q-03-23） | RPO 1 日（NFR-004）を日次バックアップで満たす。バックアップは稼働日にしか取らないため、7 世代は約 7 稼働日（暦日で 9〜11 日程度）。更新スクリプトの直前バックアップ（US-022）は 7 世代に数えず別に置く。ゴミ箱からの完全削除（削除から 30 日後）の後も、約 7 稼働日は完全削除前の世代がバックアップに残り、それを過ぎると戻せない。メモ本文の上書きはバックアップでしか戻せない（A-015） |
| NFR-010 | スケーラビリティ | 想定データ量・成長見込み | 利用者 10 人（上限の設計目安 30 人）、タスク 年 5,000 件（3 年で 15,000 件を設計目安）、メモ 1 件あたり数百〜数千文字（上限 100,000 文字。FR-005）。添付ファイルは持たない（Q-03-10） | Q-04-1・A-006。運用 1 年後に実績で見直す |
| NFR-011 | 対応環境 | 対応OS/ブラウザ/デバイス | 動作保証: PC の Chrome・Edge の最新版。Firefox・Safari は「動けばよい」程度（テストの対象外、不具合は優先度を下げて扱う）。Internet Explorer は非対応。スマートフォンのブラウザ（社内 Wi-Fi 経由。Q-02-4）では閲覧ができること（レスポンシブ表示。操作の最適化はしない）。サーバー OS は Windows 11（Q-09-12） | Q-02-3・Q-04-3 |
| NFR-012 | コスト | インフラ・運用コスト上限 | 月 0 円。既存の社内サーバー・既存の共有フォルダだけを使い、有料のホスティング・ドメイン・証明書・外部サービスを使わない。GitHub（プライベートリポジトリ）と GitHub Actions は無料枠の範囲で使い、有料の外部レビュー Action は使わない | Q-06-2・Q-09-4・Q-09-8 |
| NFR-013 | コンプライアンス | 法規制・社内ポリシー | (1) 社外秘・機密を含む可能性があるため、データは社内 LAN 内のサーバーと社内の共有フォルダにだけ置き、社外（SaaS・クラウド）に置かない（Q-04-4・Q-01-3）。(2) 個人情報は利用者の表示名とログイン ID に限り、個人情報保護法上の取り扱いは社内の既存ルールに従う。(3) 特定の業界規制の対象ではない | 社内の情報セキュリティ規程が別途あれば、設計フェーズ開始前に共有してもらう |
| NFR-014 | アクセシビリティ | 対応レベル（該当する場合） | 準拠レベルの要件は無い。一般的な配慮として、フォームの入力欄にラベルを付ける、通常の文字と背景のコントラスト比を 4.5:1 以上にする（暫定値。A-007）、期限超過・期限間近の表示を色だけに頼らない（アイコンや文字も併用する。US-013） | Q-04-6 |
| NFR-015 | 国際化 | 多言語対応の要否 | 日本語のみ。多言語対応はスコープ外。日付は日本時間・「YYYY/MM/DD」形式で表示する | Q-04-5 |

必要に応じて行を追加・削除してよい。「該当なし」も明示的に記載する（空欄のまま残さない）。
ID は `NFR-nnn` の連番（欠番を再利用しない）。設計（architecture.md §6・§7）とテスト計画（非機能テストの
「対応要件ID」）はこの ID で参照する（`tools/trace-check.py` の既定パターン `US|FR|NFR`。ID 体系は
`docs/00-overview/README.md`）。
