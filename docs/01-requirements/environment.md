# 環境・リリース自動化情報

このファイルは、リリースフェーズを自動実行するために **必須の入力** になる。
要件定義フェーズの中で必ず埋める（曖昧なまま設計・実装に進まない）。

根拠は `requirements/questionnaire.md` の Q-ID。第 2 回（Q-09-12・Q-09-13・Q-09-14・Q-10-7）の回答により、未確定だった 4 点はすべて確定した（2026-09-26）。
このファイルの「ユーザー」は、このプロジェクトの発注者（要件を決め、リリースの人手作業を行う人）を指す（glossary.md）。

## デプロイ先

| 項目 | 内容 |
|---|---|
| ホスティング/実行環境（例: Vercel, AWS, on-prem Docker, 社内サーバー等） | 社内のオンプレミスサーバー 1 台（既存の機材。Q-09-1・Q-06-2）。OS は Windows 11（Q-09-12）。平日の日中だけ電源が入り、夜間・休日は止まる（Q-09-14）。インターネットに接続できる（Q-09-13）。アプリは Windows のサービスとして登録し、起動時に自動で立ち上げる（US-019）。高速スタートアップとスリープの無効化、業務時間中の自動再起動を避ける設定（Windows Update のアクティブ時間）、Windows Defender ファイアウォールの受信許可とネットワークプロファイル（プライベート）の設定はユーザーが手作業で行う（A-019・A-023）。データベースはアプリと同じサーバーで動くアプリ同梱型とし、別のデータベースサーバーは立てない（Q-06-4）。冗長構成は取らない（NFR-003） |
| リージョン・ドメイン | リージョン: 該当なし（社内設置）。アクセス範囲: 社内 LAN からのみ、インターネットには公開しない（Q-09-2）。名前: 社内のホスト名（社内 DNS に登録。スマートフォンでも閲覧するため hosts では足りない。社内 DNS が無ければ証明書に IP アドレスの SAN を入れて IP で開く。A-016）。暗号化: 自己署名証明書による HTTPS（Q-09-3）。独自ドメイン・公的な証明書は使わない。証明書の作成・有効期限前の更新・利用者の PC とスマートフォン（Q-02-4）への信頼設定はユーザーが手作業で行う（Q-09-10・A-016）。有効期間は設計フェーズで決め、期限の日付をリリース時に `docs/05-release/` に記録して更新時期を管理する |
| CI/CDの有無・利用サービス（GitHub Actions等） | CI: あり。ソースは GitHub のプライベートリポジトリ（`origin` = `https://github.com/n-ima/todo-app.git`）に置き、GitHub Actions で自動テストとビルドを回す（Q-09-4。無料枠の範囲。NFR-012）。CD: なし。GitHub Actions からは社内 LAN のサーバーに到達しないため、サーバーへの反映は人が更新スクリプトを実行する（Q-09-6・Q-09-11）。サーバーはインターネットに接続できる（Q-09-13）ので、ユーザーがサーバー上で GitHub から配布物（ビルド済み一式）を取得し、更新スクリプトに渡す。取得の具体的な形（Release の ZIP か、タグの clone か）は設計フェーズで決める。プライベートリポジトリの認証はユーザー自身の GitHub ログインで行い、エージェントは関与しない |
| コンテナ/オーケストレーション（該当する場合） | 該当なし（要件上の必要なし。コンテナを使うかどうかは設計フェーズで、サーバー OS と既存機材に導入済みのソフトを前提に決める） |

## 認証・認可・シークレット

| 項目 | 内容 |
|---|---|
| デプロイに必要な認証情報の種類（APIキー、クラウドロールなど） | (1) 社内サーバーの OS ログインアカウント（導入・更新・復旧スクリプトを実行する人が使う）。(2) バックアップ用共有フォルダへ書き込むためのアカウント（サーバー上のバックアップ処理が使う）。(3) バックアップの暗号化鍵。(4) アプリの初期管理者パスワード（セットアップ時に人が入力し、初回ログインで変更する）。(5) GitHub Actions 用のシークレット（CI でテスト・ビルドするだけなので現時点では不要。必要になった場合だけ登録する）。クラウドの API キー・ロールは該当なし |
| シークレットの保管場所（GitHub Secrets, Vaultなど） | CI が使うシークレット: GitHub Secrets（Q-09-5）。サーバーの OS アカウント・共有フォルダのアカウント: 人が保持し（保管場所は社内の既存のアカウント管理に従う。Q-10-7 のパスワード管理ツールを使ってもよい）、リポジトリ・docs には書かない（CI からサーバーに到達しないため GitHub Secrets に置く必要が無い）。共有フォルダのアカウントはサーバー上の OS の資格情報保管機能（または実行アカウントだけが読める設定ファイル）に置く（方式は設計フェーズで OS に合わせて決める）。バックアップ暗号化鍵: サーバー上に置くものに加え、控えをパスワード管理ツールに人が保管する（Q-10-7）。いずれもリポジトリにはコミットしない |
| エージェントがアクセス可能な範囲 / アクセスできないもの | エージェントは**値を見ず、参照名だけを使う**（Q-09-11）。アクセスしてよい: GitHub Secrets の参照名（`${{ secrets.NAME }}` の記述）、スクリプトが読む設定項目の名前。アクセスしない: 上記 (1)〜(4) の値そのもの、社内サーバーへのログイン、共有フォルダ。エージェントは社内サーバー上で何も実行しない（サーバー上の操作はすべて人が行う） |

## リポジトリ側セキュリティ設定チェックリスト

エージェントは実行ツール（Bash 等）経由でファイル書き込み・git 操作ができるため、
ハーネスのフック（提案層）だけでは防げない操作がある。リポジトリ側の強制層で
塞げるものは、要件定義の時点で有効化を確認しておく（GitHub 以外のホスティングでは
相当機能の有無を確認し、無ければ「なし」と理由を記録する）。

| 設定 | 目的 | 確認 |
|---|---|---|
| Secret scanning + push protection | シークレットを含む push をサーバー側で拒否する（Bash 書き込み穴を強制層で塞ぐ唯一の手段） | [ ] 有効にする（Q-09-8）。GitHub の設定画面での操作＝人手。最初の push の前に有効化する。**個人アカウントのプライベートリポジトリでは有料プランが必要な可能性が高い（A-017。実機未確認）**。使えない場合は「なし（プラン外）」と記録し、代替として (1) GitHub Actions で無料のシークレット検出ツール（gitleaks 等。選定は設計フェーズ）を CI の必須ジョブにする、(2) ローカルの pre-commit フックで同じ検査をする、の 2 つを採る（どちらも月 0 円） |
| CodeQL（default setup） | push / PR ごとの静的解析 | [ ] 有効にする（Q-09-8）。人手（GitHub の設定画面）。プライベートリポジトリでは有料プランが必要な可能性が高い（A-017）。有効化時に確認し、使えなければ「なし（プラン外）」と記録して、代替は設計フェーズで選ぶ静的解析（lint のセキュリティ規則）を CI で回すことにする |
| Dependabot（alerts + security updates） | 依存脆弱性の検知と更新 PR | [ ] alerts を有効にする（Q-09-8）。人手（GitHub の設定画面）。security updates（自動 PR）の採否は設計フェーズで決める |
| ブランチ保護 + CODEOWNERS | 保護ブランチへの直接 push 禁止・重要パスのレビュー必須化 | [ ] 付けない（Q-09-8「1 人開発のうちは付けない」）。開発者が 2 人以上になったら再検討する |
| （クライアント側）security-guidance プラグイン | 実装中の差分レベルのセキュリティ助言（本ハーネスの release-security-review スキルはリリースゲート統合専用で、検出はビルトイン層が正） | [ ] 質問票では聞いていない。導入するかは人が判断する（入れない場合もリリース前の `release-security-review` は必ず行う） |
| claude-code-security-review Action の採否 | PR ごとの自動セキュリティレビュー（`.github/workflows/` の `.example`。API 費用がかかるため採否を理由つきで判断・記録する） | [ ] 採用しない（Q-09-8「有料の外部レビュー Action は使わない」。月 0 円の制約。NFR-012） |

## 自動化できる/できない境界

エージェントが実際にリリースを自動実行するにあたり、**どこまでを自動化してよいか**を明確にする。

| 作業 | 自動化可否 | 理由・人手が必要な場合の担当 |
|---|---|---|
| ビルド・パッケージング | 自動 | Q-09-6。ローカルと GitHub Actions でビルドし、配布物を作るところまでエージェントが確認なしで進めてよい |
| テスト実行 | 自動 | Q-09-6。ローカルと GitHub Actions で実行する |
| デプロイ（インフラへの反映） | 人手 | Q-09-6 で自動に選ばれていない。GitHub Actions から社内サーバーに到達しない。エージェントは更新手順（どの配布物を・どのコマンドで）を提示し、ユーザーが社内サーバーで更新スクリプト（US-022）を実行する。初回はセットアップスクリプト（US-019）。社内ホスト名の登録・自己署名証明書の作成と更新・利用者の PC・スマートフォンへの証明書の信頼設定、サーバーのスリープ無効化もユーザーが手作業で行う（Q-09-10・Q-02-4・A-019） |
| DBマイグレーション | 人手（承認制） | Q-09-9「SQL を提示して承認を得てから適用する」。エージェントはスキーマ変更の SQL を用意し、更新スクリプトが適用前に SQL を表示して実行者の承認を求める。適用するのは更新スクリプトを実行した人 |
| 監視・アラート設定 | 該当なし | 自動の障害検知・アラート通知は作らない（Q-04-11）。エラーログのファイル出力（90 日保持）はアプリの機能として実装する（NFR-008） |
| 本番切り替え（カットオーバー） | 人手 | Q-09-6 で自動に選ばれていない。利用開始の案内（URL・初期パスワードの配布）はユーザーが行う |

「人手」に分類した項目は、リリースエージェントが該当ステップで作業内容を提示し、
ユーザーに実行してもらってから先に進む。

**「自動」の意味（承認の規範は AGENTS.md が正）**: 「自動」は「エージェントが準備（ビルド・
パッケージング・dry-run / plan・ローカル検証・チェックリスト作成）まで確認なしに進めてよい」
という意味であり、**外部反映（push・タグ付け・デプロイ・公開・公開 API の書込）そのものは
分類に関わらず必ずユーザーの exact-action 承認（何を・どこへ・どの引数）を経る**。承認の単位は
`docs/05-release/release-checklist.md` の action packet の行で、フック（guard-dangerous-git /
guard-external-effect）が実行時にも同じ単位で確認を入れる。「自動」に分類したからといって
承認が省略されることはない。

## 利用者の運用作業の自動化境界（配布型アプリでは省略不可）

上の表は開発・リリース作業の境界。これとは別に、**利用者側の運用作業**に
どこまで手作業を残してよいかを確認する（**「手順書に書く」は自動化の代替ではない**。
この方針が不明のまま進み、リリース直前に「すべて自動にする」方針が判明して
更新スクリプトの要件が急遽追加された実例あり）。

| 利用者の作業 | 自動 / 手作業 | 備考（スクリプト提供の有無等） |
|---|---|---|
| 初期導入（インストール） | 自動（スクリプト） | セットアップスクリプトを提供する。データベース初期化・初期状態の作成・管理者利用者の作成・Windows のサービス登録（自動起動）まで 1 コマンドで行う（Q-10-1・US-019）。スクリプトの実行と、前提ソフトの導入・ホスト名登録・証明書作成は人が行う |
| バージョン更新（2回目以降のインストール） | 自動（スクリプト） | 更新スクリプトを提供する。停止 → バックアップ → 入れ替え → スキーマ変更（SQL を表示して承認制） → 起動を 1 コマンドで行う（Q-10-2・US-022）。**更新後も既存データ（タスク・メモ・利用者・状態・履歴・ゴミ箱）が引き継がれることをテストの対象にする**。計画停止は 30 分以内（NFR-003） |
| バックアップ | 自動（毎日） | サーバーは日中だけ動く（Q-09-14）ため、毎日その日最初のアプリ起動時に自動実行し（US-019・US-020）、暗号化して社内の別サーバーのバックアップ用共有フォルダへ置く。7 世代保持（Q-10-3・Q-10-5・Q-10-6・US-020）。成否は管理画面で確認する（アラート通知はしない） |
| 復旧（リストア） | 自動（スクリプト・確認つき） | 復旧スクリプトを提供する。戻す世代を選び、実行前に確認を求め、置き換え前のデータを退避してから戻す（Q-10-4・US-020）。実行は人が行う |
| サーバーの電源の入り切り | 手作業（毎日） | ユーザーが平日の朝に電源を入れ、終業時にシャットダウンする（Q-09-14）。アプリとバックアップは電源投入後に自動で動く（US-019・US-020）。BIOS のタイマー起動などで自動化する余地はあるが、要件にはしない |

## ロールバック方針

- 失敗時にどこまで自動でロールバックしてよいか: アプリの入れ替え（スキーマ変更なし）に失敗した場合、更新スクリプトは自動で 1 つ前の版に戻して起動してよい（Q-09-7・US-022）。リリース作業全体では、タグの打ち直しや履歴の書き換えによるロールバックは行わず、修正版を新しい版として出す。
- 人手でのロールバック判断が必要なケース: データベースのスキーマを変更した後の失敗（データ損失を伴いうるため、必ず人が判断する。Q-09-7）。更新スクリプトは更新前バックアップの場所と戻し方を表示して止まり、人が復旧スクリプトで戻すかを決める。

## この環境向けの既存Skillの有無

`.github/skills/deploy-<environment>/SKILL.md` に該当する手順が既にあるか確認する。
なければリリースフェーズで `skill-authoring` スキルを使って新規作成する
（`.github/skills/skill-authoring/SKILL.md` 参照）。

- 該当する既存Skill: なし。既存の `deploy-local-npx`（npx でのローカル起動）と `deploy-local-zip`（Git タグと git archive による ZIP 配布）はどちらも「ホスティング先を持たないローカル実行アプリ」向けで、社内サーバーへの導入・更新スクリプト・定期バックアップを含まない。リリースフェーズで `skill-authoring` スキルにより `deploy-onprem-server`（仮称）を新規作成する。配布物の作り方と検査（タグ・ZIP・CI の成果物の検査）は `deploy-local-zip` の手順を流用できる。
