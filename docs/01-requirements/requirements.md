# 要件定義書

入力: `requirements/memo.md`、`requirements/questionnaire.md`（第 1 回 76 問 2026-09-23・第 2 回 8 問 2026-09-26、全 84 問回答済み）。
各記述の末尾の `(Q-xx-n)` は根拠となった質問票の ID。

## 1. 目的・背景

- なぜこのアプリを作るのか（解決したい課題）: いまはタスクが Excel・紙・個人のメモアプリに分散していて、誰が何をどこまで進めたかが分からず、共有もしづらい（Q-01-1）。「これさえ解決できれば作った甲斐がある」のは、**階層で整理されたタスクの現状（誰が・いつまでに・どこまで）が、1 画面で全員に見えること**（Q-01-2）。
- 誰の・どんな困りごとか: 同じ職場のチーム（最大 10 人程度）が抱える課題。リーダーは遅れを一目で把握できず、メンバーは作業記録の置き場が無く、管理者はデータの保全手段を持っていない（§3 のペルソナ）。
- 既製品を使わず自作する理由: 社外 SaaS にデータを置けない（社外秘を含む。Q-04-4）、費用をかけられない（月 0 円。Q-06-2）、欲しい機能だけを持つ小さいものが欲しい（Q-01-3）。
- 参考にするサービス: メモは Notion、階層タスクは Backlog / Asana（Q-01-3）。

## 2. スコープ

### やること

memo.md の 5 本柱と、質問票の回答で決まった範囲。優先度は §5 の各 US を正とする（MoSCoW。Q-03-28）。

- 階層タスク管理: 最上位「プロジェクト」の下に、タスクが子タスクを無制限に入れ子で持つ（Q-03-1）。
- 一覧（階層ツリー）と絞り込み・並び替え・検索、期限超過の強調表示（Q-03-21・Q-11-5）。
- タスク 1 件ごとの Markdown メモ（プレビュー表示）（Q-03-9・Q-03-11・Q-03-29）。
- タスク 1 件単位の編集ロック（明示取得・30 分無操作で自動解放・管理者の強制解除）（Q-03-17〜20）。
- ID とパスワードによるログイン、管理者 / 一般利用者の 2 ロール（Q-02-2・Q-03-25）。
- ゴミ箱（30 日間は復元できる論理削除）（Q-03-23）。
- カレンダー表示（月・週。閲覧専用）（Q-03-5・Q-03-6）。
- 状態の並び（ワークフロー）を管理者が定義する機能（アプリ全体で 1 つ）（Q-03-12・Q-03-13）。
- 画面内の通知一覧（担当割り当て・期限の前日と当日）（Q-03-15・Q-03-16・A-020）。
- 変更履歴（状態変更・担当変更・ロック強制解除）（Q-03-24）。
- タスク一覧の CSV 書き出し（Q-03-30）。
- 利用者側の運用スクリプト: 初期導入・更新・毎日の自動バックアップ・復旧（Q-10-1〜Q-10-6）。

### やらないこと（スコープ外）

Q-05-1 でユーザーが明示的に選んだもの:

- リアルタイム共同編集（同時編集はロックで排他する。memo.md 23 行目）
- スマホ専用アプリ（スマホはブラウザでの閲覧のみ。NFR-011）
- 工数・作業時間の記録
- ガントチャート
- 外部サービス連携（Google カレンダー・Outlook・Slack・Teams・LINE・メール送信を含む。Q-03-8・Q-03-15）
- タスクへのコメント欄（メモとは別の時系列コメント。Q-11-2）
- チャット・掲示板機能
- ファイル共有機能
- レポート・集計グラフ

回答から決まったもの:

- 画像・ファイルの添付（Q-03-10「当面は不要」）
- Notion 型のブロックエディタ（WYSIWYG・スラッシュコマンド）。メモは Markdown 記法で書く（Q-03-9）
- メモの表（Markdown テーブル）（Q-03-29）
- タスクから独立したメモページ（Q-03-11）
- 承認フロー・自動化ルールとしてのワークフロー（Q-03-12 は「状態の並びの定義」を選択）
- プロジェクトごとに異なるワークフロー（MVP 外。Q-03-13 の回答は「アプリ全体で 1 つ」のみ）
- 状態遷移の順序制約（Q-03-14。状態を変更できる人は §5.0 の編集権限に従う）
- 親タスクの進捗・期限を子から自動計算すること（Q-03-2）
- タグ（Q-03-3）
- 繰り返しタスクの自動生成（Q-03-7）
- 自動アーカイブ（Q-03-22）
- インターネットからのアクセス（社内 LAN のみ。Q-09-2）
- 多言語対応（日本語のみ。Q-04-5）
- 自動の障害検知・アラート通知（Q-04-11）
- 利用者の自由サインアップ・招待リンク（Q-03-26）

## 3. 想定ユーザー・利用シーン

- 想定ユーザー像: 同じ職場のチーム。全員が互いを知っており、悪意のある利用者は想定しない（Q-02-1）。同時利用は最大 10 人（Q-04-1）。ロールは「管理者」と「一般利用者」の 2 種類（Q-02-2）。
- 主な利用シーン（Who / When / Where）:
  - **P1 リーダー**（管理者ロールで使う。Q-03-32。週に数回、朝）: 社内の PC ブラウザで一覧・カレンダーを開き、期限超過のタスクを見つけ、メモで遅れの理由を確かめ、担当と期限を付け直す。
  - **P2 メンバー**（一般利用者。毎日、日に何度も）: 自分の担当タスクを開いてロックを取り、メモに作業記録を書き足し、状態を進める。離席してロックを握ったままになることがある。
  - **P3 管理者**（月に数回）: 利用者の追加、ワークフロー（状態）の定義、ロックの強制解除、サーバー障害や PC 故障時の復旧を行う。
- 端末: PC のブラウザが主。スマートフォンはブラウザで「見るだけ」（Q-02-3）。スマートフォンは社内 Wi-Fi 経由で開け、自己署名証明書を端末に信頼させてよい（Q-02-4。信頼設定は人手。environment.md）。
- 主用途は「見る」。ログイン直後の画面はタスク一覧（Q-11-4）。

## 4. 成功指標

- このアプリがうまくいったと言える基準（運用開始から数か月後に `/10-retrospective` で判定。Q-07-1）:
  1. メンバー全員が週に数回は自分でアプリを開いている（判定方法: 利用者への聞き取り）。
  2. 「あれどうなった？」を口頭で聞く回数が減ったと、リーダーが感じている（判定方法: リーダーへの聞き取り）。
  3. 期限切れに気づかず放置されるタスクが無い（判定方法: 期限超過のまま最終更新日時（US-004 の項目）から 1 週間以上経ったタスクが 0 件）。

## 5. ユーザーストーリー

各ストーリーは以下の形式で記述する（ID は `US-nnn` の連番。EARS の個別要求文に ID を付ける場合は
`FR-nnn`。非機能要件は nfr.md の `NFR-nnn`、前提・リスクは §7 の `A-nnn`。下流の設計・タスク・テストは
この ID で参照し、`tools/trace-check.py` が整合を検査する。ID 体系の一覧は `docs/00-overview/README.md`）。

```
### US-001: <タイトル>
- 優先度: Must / Should / Could
- ストーリー: 〜として、〜したい。なぜなら〜だからだ。
- 受け入れ条件:
  - Given <前提> When <操作> Then <結果>
  - Given <前提> When <操作> Then <結果>（異常系）
```

### 5.0 権限の共通規則（全 US に適用）

「編集権限」を次のとおり定義し、各 US の「編集できる人」はこれを指す（Q-03-27・Q-02-2）。

| 操作 | 管理者 | 一般利用者 |
|---|---|---|
| 全プロジェクト・全タスクの閲覧 | できる | できる |
| プロジェクトの作成・名前変更・削除 | できる | できない（A-001） |
| タスクの新規作成（任意の親の下に） | できる | できる（A-002） |
| 担当者が自分のタスクの編集・移動・削除 | できる | できる |
| 担当者が他人のタスクの編集・移動・削除 | できる | できない |
| 担当者が未設定のタスクの編集・移動・削除 | できる | できる（Q-03-31。担当者を自分にしてから作業する運用も可） |
| 配下に自分が編集できないタスクを含むタスクの移動・削除 | できる | できない（A-013） |
| ゴミ箱からの復元 | できる | 自分が削除したものだけ |
| CSV 書き出し | できる | できる（A-014） |
| ロックの強制解除・利用者管理・ワークフロー定義 | できる | できない |

- FR-001: 編集権限の無い利用者がタスクの編集・移動・削除・ロック取得を要求したとき、システムはその要求を拒否し、「このタスクを編集できるのは担当者と管理者だけです」と表示しなければならない（画面上の操作ボタンは無効表示にし、API 直接呼び出しでも拒否する）。
- 「管理者」はアプリのロールを指す。§5.10 のスクリプトを社内サーバーで実行する人は「サーバー運用者」と呼んで区別する（多くの場合同じ人が兼ねる）。

### 5.1 ログイン・利用者管理

### US-001: ログインする

- 優先度: Must
- ストーリー: 利用者として、ID とパスワードでログインしたい。なぜなら、誰の操作かを記録し、編集権限を区別する必要があるからだ（Q-03-25）。
- 受け入れ条件:
  - Given 登録済みの有効な利用者 When 正しいログイン ID とパスワードを入力する Then ログインでき、タスク一覧（US-005）が表示される
  - Given 登録済みの利用者 When 誤ったパスワードを入力する Then ログインできず、ID とパスワードのどちらが誤りかを区別しない文言で失敗を表示する（異常系）
  - Given 同じログイン ID で連続 5 回ログインに失敗した When 6 回目を試みる Then 15 分間はパスワードが正しくてもログインできず、その旨を表示する（異常系・境界値。回数・時間は暫定値＝NFR-005）
  - Given 無効化された利用者 When 正しい ID とパスワードでログインする Then ログインできない（異常系）
  - Given ログイン中 When 最後の操作から 8 時間操作が無い Then 次の操作でログイン画面に戻る（暫定値＝NFR-005）
  - Given 未ログイン When いずれかの画面の URL を直接開く Then ログイン画面へ遷移する（異常系）

### US-002: 初回ログイン時にパスワードを変更する

- 優先度: Must
- ストーリー: 利用者として、管理者から渡された初期パスワードを自分のものに変えたい。なぜなら、初期パスワードは管理者も知っているからだ（Q-03-26）。
- 受け入れ条件:
  - Given 初期パスワードのままの利用者 When ログインする Then パスワード変更画面が表示され、変更するまで他の画面へ進めない
  - Given パスワード変更画面 When 8 文字未満、または初期パスワードと同じ値を入力する Then 変更できず理由を表示する（異常系・境界値。文字数は暫定値＝NFR-005）
  - Given ログイン中の利用者 When 自分のパスワード変更画面で現在のパスワードと新しいパスワードを入力する Then パスワードが変わる

### US-003: 管理者が利用者を登録・変更・無効化する

- 優先度: Must
- ストーリー: 管理者として、管理画面から利用者を登録し、辞めた人を無効化したい。なぜなら、サインアップ画面を設けず、利用者を管理者が把握するからだ（Q-03-26）。
- 受け入れ条件:
  - Given 管理者 When ログイン ID・表示名・ロール（管理者 / 一般）・初期パスワードを入力して登録する Then 利用者が作られ、初回ログイン時にパスワード変更を求められる状態になる
  - Given 管理者 When 既に存在するログイン ID で登録する Then 登録できず重複を表示する（異常系）
  - Given 管理者 When 利用者を無効化する Then その利用者はログインできなくなり、担当しているタスクの担当者欄は「（無効）表示名」と表示される。タスクは消えない
  - Given 管理者 When パスワードを忘れた利用者に新しい初期パスワードを設定する Then その利用者は次回ログイン時にパスワード変更を求められる
  - Given 管理者が自分 1 人だけ When 自分を一般利用者に変更、または無効化しようとする Then 拒否し「管理者が 1 人もいなくなります」と表示する（異常系）
  - Given 一般利用者 When 管理画面の URL を直接開く Then アクセスを拒否する（異常系）

### 5.2 プロジェクト・タスク（階層）

### US-004: プロジェクトとタスクを階層で登録する

- 優先度: Must
- ストーリー: 利用者として、プロジェクトの下にタスクを作り、タスクの下に子タスクを何段でも作りたい。なぜなら、大きな仕事を分解して管理したいからだ（memo.md 19 行目・Q-03-1）。
- 受け入れ条件:
  - Given 管理者 When プロジェクト名を入力して作成する Then 一覧の最上位にプロジェクトが表示される
  - Given 利用者 When プロジェクトまたはタスクの下で、タイトルを入力してタスクを作成する Then その直下に子タスクとして作られる。状態はワークフローの先頭の状態になる
  - Given 利用者 When タイトルを空のままタスクを作成する Then 作成できず「タイトルは必須です」と表示する（異常系）
  - Given 5 段以上の入れ子 When さらに子タスクを作成する Then 段数の上限なく作成できる（境界値）
- 項目（Q-03-3）: タイトル（必須）、状態（必須）、担当者（0〜1 人）、開始日（任意）、期限（任意）、優先度（高・中・低。既定は中）、メモ本文、親（プロジェクトまたはタスク）。タグは持たない。加えてシステムが作成者・作成日時・最終更新者・最終更新日時を自動で記録し、詳細画面に表示する（§4 成功指標 3 の測定に使う）。
- FR-002: 利用者が開始日より前の期限を保存しようとしたとき、システムは保存を拒否し「期限は開始日以降にしてください」と表示しなければならない。

### US-005: タスクを階層ツリーの一覧で見る

- 優先度: Must
- ストーリー: 利用者として、全プロジェクトのタスクを階層のまま 1 画面で見たい。なぜなら、誰が・いつまでに・どこまで進めたかを全員で共有したいからだ（Q-01-2）。
- 受け入れ条件:
  - Given ログイン直後 When 一覧画面が開く Then 全プロジェクトのタスクが階層ツリーで表示され、各行にタイトル・状態・担当者・期限・優先度が出る
  - Given 一覧画面 When 初めて表示する Then プロジェクトの直下のタスクを 1 段目として 3 段目のタスクまで展開され、4 段目以降は折りたたまれている（Q-03-1。境界値: 3 段目は見え、4 段目は見えない）
  - Given 一覧画面 When 折りたたまれた行の展開ボタンを押す Then 子タスクが表示される
  - Given 一覧画面 When タスク名をクリックする Then そのタスクの詳細画面（US-006）へ遷移する（Q-11-3）
  - Given 完了扱いの状態のタスク When 一覧を表示する Then 既定では表示されず、「完了も表示」をオンにすると表示される（Q-03-22）
  - Given 完了扱いのタスクの下に未完了の子タスクがある When 「完了も表示」がオフ Then 親は薄く表示され、未完了の子タスクは表示される（異常系・境界値。子が親ごと隠れて見落とされるのを防ぐ）
  - Given プロジェクトもタスクも 0 件 When 一覧を開く Then 「タスクがありません」と表示する（境界値）

### US-006: タスクの内容を編集する

- 優先度: Must
- ストーリー: 担当者または管理者として、タスクの項目を変更したい。なぜなら、進捗・担当・期限は日々変わるからだ（P1・P2）。
- 受け入れ条件:
  - Given 編集権限のある利用者がそのタスクのロックを持っている（US-010） When タイトル・状態・担当者・開始日・期限・優先度を変更して保存する Then 変更が保存され、ロックが解放される
  - Given 編集権限の無い利用者 When タスク詳細を開く Then 全項目を閲覧でき、編集ボタンは無効になっている（FR-001）
  - Given 未完了の子タスクを持つタスク When その状態を完了扱いの状態へ変更して保存する Then 「未完了の子タスクが n 件あります。完了にしますか」と警告し、利用者が了承した場合だけ保存する（Q-03-2）
- FR-003: 親タスクの状態・期限・進捗は子タスクから自動計算してはならない。親は親で独立に値を持つ（Q-03-2）。

### US-007: タスクを別の親へ移動する・並び順を変える

- 優先度: Must
- ストーリー: 担当者または管理者として、タスクを別のプロジェクトや別の親タスクの下へ移したい。なぜなら、作業の分け方は途中で変わるからだ（Q-03-4）。
- 受け入れ条件:
  - Given 編集権限のある利用者 When タスクの「移動」メニューで移動先（プロジェクトまたはタスク）を選ぶ Then タスクは子タスクごと移動先の直下へ移る
  - Given タスク A When 移動先に A 自身または A の子孫を選ぶ Then 移動を拒否し「自分自身や配下のタスクの下には移動できません」と表示する（異常系）
  - Given 移動対象のタスク、または配下の子タスクを他人がロック中 When 移動する Then 移動を拒否し、ロック中の利用者名を表示する（異常系）
  - Given 一般利用者が、配下に自分が編集できないタスク（他人が担当）を含むタスク When 移動する Then 移動を拒否し、編集できないタスクの一覧を表示する（異常系。A-013）
  - Given 移動対象の編集権限はあるが移動先の親（他人が担当）の編集権限は無い利用者 When その親の下を移動先に選ぶ Then 移動できる（子を持つことは親の編集にあたらない。A-002 と同じ解釈）
  - Given 並び順が「手動順」の一覧 When 「上へ」「下へ」を選ぶ Then 同じ親の中で順番が入れ替わる（A-004）

### US-008: タスクを削除し、ゴミ箱から戻す

- 優先度: Must
- ストーリー: 利用者として、誤って消したタスクを 30 日以内なら自分で戻したい。なぜなら、消したデータは取り返しがつかないからだ（Q-03-23）。
- 受け入れ条件:
  - Given 編集権限のある利用者 When タスクを削除し確認ダイアログで了承する Then タスクは子タスクごとゴミ箱へ移り、一覧・カレンダー・検索に出なくなる
  - Given 配下に他人がロック中のタスクがある When 削除する Then 削除を拒否し、ロック中の利用者名を表示する（異常系）
  - Given 一般利用者が、配下に自分が編集できないタスク（他人が担当）を含むタスク When 削除する Then 削除を拒否し、編集できないタスクの一覧を表示する（異常系。A-013）
  - Given メモ本文を消去・上書きして保存した When 元の内容に戻したい Then ゴミ箱の対象外で、変更履歴にも残らないため、戻す手段はバックアップからの復旧（US-020）だけである（仕様の明示。Q-03-23 はタスクの削除を対象とする。A-015）
  - Given ゴミ箱のタスク When 削除した本人または管理者が「元に戻す」を選ぶ Then 子タスクとメモごと元の親の下へ戻る
  - Given 元の親がゴミ箱にある、または完全削除済み When 子だけを戻そうとする Then 戻さずに「元の親が存在しません。先に親を戻すか、管理者に相談してください」と表示する（異常系）
  - Given ゴミ箱に入ってから 30 日を過ぎたタスク When 日次処理が動く（アプリ起動中の日付変更時、またはその日最初の起動時。US-019） Then システムはそのタスクを完全に削除する（境界値: 30 日目までは戻せる）
  - Given 管理者 When プロジェクトを削除する Then プロジェクトは配下のタスクごとゴミ箱へ移り、管理者だけが戻せる
- FR-004: 削除されたタスクの完全削除は、ゴミ箱に入った日から 30 日を過ぎたときにだけ行い、それ以外の経路で利用者がデータを完全削除する手段を設けてはならない（管理者によるバックアップからの復旧 US-020 は除く）。

### 5.3 メモ

### US-009: タスクに Markdown でメモを書く

- 優先度: Must
- ストーリー: 利用者として、タスクごとに 1 つの常設メモへ作業記録を Markdown で書き、整形されたプレビューで読みたい。なぜなら、遅れの理由や経緯をタスクと一緒に残したいからだ（memo.md 24 行目・Q-03-9・Q-03-11・Q-11-2）。
- 受け入れ条件:
  - Given ロックを持つ利用者 When メモに Markdown を書いて保存する Then 詳細画面に整形されたプレビューとして表示される
  - Given メモ編集中 When 編集欄とプレビューを切り替える（または並べて表示する） Then 保存前でも整形結果を確認できる
  - 対応する書式（Q-03-29）: 見出し、箇条書き・番号付きリスト、チェックボックス、太字・斜体・取り消し線、コードブロック、他のタスクへのリンク。表は対応しない
  - Given メモに他のタスクへのリンクを書いた When プレビューでリンクをクリックする Then リンク先タスクの詳細画面へ遷移する
  - Given リンク先のタスクがゴミ箱にある、または完全削除済み When プレビューを表示する Then リンクは「（削除されたタスク）」と表示され遷移しない（異常系）
  - Given メモに `<script>` 等の HTML を書いた When プレビューを表示する Then HTML は実行されず、文字列として表示される（異常系。NFR-007）
  - Given ロックを持つ利用者 When 編集欄でチェックボックスの `[ ]` を `[x]` に書き換えて保存する Then プレビューのチェックボックスがチェック済みで表示される
  - Given ロックを持たない利用者（ロック保持者本人の閲覧表示も含む） When プレビュー上のチェックボックスをクリックする Then 状態は変わらない（プレビューは表示専用。異常系）
- FR-005: システムはメモ本文を最大 100,000 文字まで保存できなければならない。もし超えて保存しようとしたならば、システムは保存を拒否し上限を表示しなければならない（上限は暫定値。Q-04-1 の「数百〜数千文字」に余裕を持たせた値）。

### 5.4 編集ロック

### US-010: タスクのロックを取って編集する

- 優先度: Must
- ストーリー: 利用者として、編集を始めるときにタスクをロックしたい。なぜなら、同時編集はせず、ロックで上書き事故を防ぐからだ（memo.md 23 行目・Q-03-17・Q-03-18）。
- 受け入れ条件:
  - Given 誰もロックしていないタスクと編集権限のある利用者 When 「編集する」を押す Then ロックを取得し、項目とメモが編集可能になる。ロックはそのタスク 1 件（メモ本文を含む）に対してかかり、子タスクには及ばない
  - Given ロック中の利用者 When 「保存」または「キャンセル」を押す Then ロックが解放される
  - Given 他の利用者がロック中 When 詳細を開く Then 内容は閲覧でき、「◯◯さんが編集中（HH:MM から）」と表示され、編集ボタンは無効になる（Q-03-19）
  - Given 2 人がほぼ同時に「編集する」を押す When サーバーが処理する Then 片方だけがロックを取得し、もう片方には「◯◯さんが編集中」と表示される（異常系・競合）
  - Given ロック中で内容を変更している When 最後の自動保存から 60 秒以内（暫定値。A-007） Then 編集中の内容がサーバーへ自動保存される（下書きの元になる。保存とは別で、他の人にはまだ見えない）
  - Given ロック中 When サーバーが最後に自動保存・保存・キャンセルのいずれかを受け取ってから 30 分経つ Then ロックは自動で解放され、最後に自動保存された内容が本人専用の下書きとして残る（境界値: 29 分では解放されない。画面を開いているだけで内容を変えていなければ「無操作」に数える）
  - Given 下書きの残るタスク When 本人が次に「編集する」を押す Then 下書きを復元するか破棄するかを選べる。復元時、下書き作成後に他の人が更新していた場合は「下書き作成後に ◯◯さんが更新しています」と表示し、どちらの内容で保存するか本人が選ぶ
  - Given ロックが自動解放された、または強制解除された後 When 元の利用者が保存を押す Then 保存を拒否し、入力内容を下書きとして残して「ロックが解除されています」と表示する（異常系）
  - Given ロック中 When ブラウザのタブを閉じる Then ロックは 30 分の自動解放まで保持され、最後に自動保存された内容が下書きになる
  - Given ロック中 When ログアウトする Then ロックは即時に解放され、最後に自動保存された内容が下書きとして残る

### US-011: 管理者がロックを強制解除する

- 優先度: Must
- ストーリー: 管理者として、他人が握ったままのロックを解除したい。なぜなら、自動解放の 30 分を待てない場面があるからだ（Q-03-20・P2）。
- 受け入れ条件:
  - Given 他人がロック中のタスク When 管理者が「ロックを強制解除」を押し確認ダイアログで了承する Then ロックが解放され、元の利用者の編集中内容は下書きとして残る
  - Given 強制解除が行われた When 保存されたデータを確認する Then 「日時・解除した管理者・元のロック保持者」が変更履歴として記録されている（Q-03-24。画面での閲覧は US-017＝Should。記録は本 US の範囲で Must）
  - Given 一般利用者 When 他人がロック中のタスクを開く Then 強制解除ボタンは表示されない（異常系）

### 5.5 絞り込み・検索・表示規約

### US-012: 一覧を絞り込み・並び替え・検索する

- 優先度: Must（メモ本文の全文検索のみ Could）
- ストーリー: 利用者として、担当者・状態・期限でタスクを絞り込みたい。なぜなら、全体から自分や遅れているタスクだけを素早く見たいからだ（Q-03-21）。
- 受け入れ条件:
  - Given 一覧画面 When 担当者・状態・期限の範囲のいずれか（複数の組み合わせ可）で絞り込む Then 条件に合うタスクだけが表示され、その祖先はツリー構造を保つために薄く表示される
  - Given 一覧画面 When 「自分の担当だけ」をオンにする Then 自分が担当者のタスクだけが表示される。既定はオフ（Q-11-3）
  - Given 一覧画面 When タイトルのキーワードを入力して検索する Then タイトルにその文字列を含むタスクが表示される（大文字・小文字、全角・半角の扱いは設計で決定）
  - Given 一覧画面 When 並び順を選ぶ Then 「期限の昇順（既定。期限なしは末尾）」「手動順」を切り替えられる（Q-11-3・A-004）
  - Given 条件に合うタスクが 0 件 When 絞り込む Then 「条件に合うタスクがありません」と表示する（境界値）
  - Given 一覧で絞り込み条件を設定した When カレンダー画面へ切り替える Then 同じ条件がカレンダーにも適用されている（Q-11-3）
  - （Could）Given 一覧画面 When 「メモも検索」をオンにしてキーワード検索する Then メモ本文にその文字列を含むタスクも表示される
- 優先度の決め方: 全文検索は Q-03-21 の仮回答では Should、Q-03-28 の仮回答では Could と食い違っていた。MoSCoW を直接聞いた Q-03-28 を優先して Could とした（A-005）。

### US-013: 期限超過・期限間近を目立たせる

- 優先度: Must
- ストーリー: リーダーとして、朝に一覧を開いた瞬間に遅れているタスクに気づきたい。なぜなら、遅れの発見が遅いと対処が間に合わないからだ（P1・Q-11-5）。
- 受け入れ条件:
  - Given 期限が昨日以前で完了扱いでないタスク When 一覧・詳細・カレンダーを表示する Then 行と期限の日付が赤で表示され、色に加えて「期限超過」のアイコンまたは文字が付く（NFR-014）
  - Given 期限が今日または明日で完了扱いでないタスク When 同じく表示する Then 黄色の印と「期限間近」のアイコンまたは文字が付く（境界値: 明後日が期限のタスクには付かない）
  - Given 完了扱いのタスク When 期限を過ぎている Then 赤・黄の強調はしない（境界値）
  - Given 一覧画面 When 表示する Then 先頭に「期限超過 n 件」（現在の絞り込み条件に関係なく全タスクで数えるか、絞り込み後で数えるかは設計で決定）が出て、クリックで期限超過のタスクに絞り込める
  - 日付の判定はサーバーのタイムゾーン（日本時間）の暦日で行う

### 5.6 カレンダー

### US-014: カレンダーでタスクの期間を見る

- 優先度: Should
- ストーリー: 利用者として、タスクの開始日から期限までを月・週のカレンダーで見たい。なぜなら、時期の重なりや締切の集中を把握したいからだ（memo.md 20 行目・Q-03-5）。
- 受け入れ条件:
  - Given 開始日と期限の両方があるタスク When 月表示・週表示を開く Then 開始日から期限までが帯で表示される
  - Given 開始日が無く期限だけがあるタスク When 表示する Then 期限日に点（1 日分の印）で表示される
  - Given 期限が無いタスク When 表示する Then カレンダーには表示されない（境界値）
  - Given カレンダー When 前月・次月（週表示なら前週・次週）へ移動する Then その期間のタスクが表示される
  - Given カレンダー When タスクをクリックする Then タスク詳細画面へ遷移する（Q-11-3）
  - Given 完了扱いのタスク When 表示する Then 既定では表示せず、「完了も表示」で表示される（Q-03-22）
  - Given 1 日に多数のタスクが重なる When 月表示する Then 「他 n 件」とまとめて表示し、クリックで一覧できる（境界値。表示件数の閾値は設計で決定）
- FR-006: カレンダーは閲覧専用でなければならない。カレンダー上での日付変更・新規作成は提供しない（Q-03-6。日付のドラッグ変更は US-021）。日表示は作らない（Q-03-5）。

### 5.7 ワークフロー（状態の定義）

### US-015: 管理者が状態の並び（ワークフロー）を定義する

- 優先度: Should（定義画面が未実装の段階では、初期状態「未着手 → 進行中 → 完了」を固定で使う）
- ストーリー: 管理者として、チームの仕事の進め方に合わせてタスクの状態の並びを定義したい。なぜなら、「未着手・進行中・完了」だけではチームの実態に合わないことがあるからだ（memo.md 25 行目・Q-03-12・Q-03-13）。
- 受け入れ条件:
  - Given 初期導入直後 When 状態の一覧を見る Then 「未着手」「進行中」「完了」の 3 つがこの順で定義され、「完了」が完了扱いになっている
  - Given 管理者 When 状態を追加・名前変更・並べ替えする Then アプリ全体（全プロジェクト）の状態の選択肢と表示順に反映される
  - Given 管理者 When 状態ごとに「完了扱い」の印を付け外しする Then 完了の非表示（US-005）・期限超過の判定（US-013）・親の完了警告（US-006）がその印に従う
  - Given いずれかのタスクが使っている状態 When 管理者が削除しようとする Then 削除を拒否し「この状態のタスクが n 件あります」と表示する（異常系）
  - Given 完了扱いの状態が 1 つだけ When その印を外す、または削除する Then 拒否し「完了扱いの状態が 1 つ以上必要です」と表示する（異常系）
  - Given 状態が 1 つだけ When 削除する Then 拒否する（境界値）
- FR-007: 編集権限（§5.0）を持つ利用者は、タスクの状態を定義済みのどの状態へも順序に関係なく変更できなければならない。遷移の順序制約は設けない（Q-03-14）。Q-03-14 の仮回答「担当者以外も変更できる」は明示回答 Q-03-27 と食い違うため採用せず、変更できる人は §5.0 に従う（他人のタスクを付け直すリーダー役は管理者ロールで運用する。Q-03-32）。

### 5.8 通知

### US-016: 画面内の通知一覧で気づく

- 優先度: Should
- ストーリー: 利用者として、自分に割り当てられたタスクや期限が近い（明日・今日）タスクを、アプリを開いたときに通知一覧で知りたい。なぜなら、担当変更や期限を口頭で伝え合わずに済ませたいからだ（Q-03-15・Q-03-16・P1）。
- 受け入れ条件:
  - Given 他の利用者 X When X が利用者 A をタスクの担当者に設定して保存する Then A の通知一覧に「X さんが『タスク名』の担当をあなたにしました」が追加される
  - Given 利用者 A When 自分で自分を担当者に設定する Then 通知は作られない（境界値）
  - Given A が担当で完了扱いでない、期限が明日のタスク When 日次処理が動く（アプリ起動中の日付変更時、またはその日最初の起動時。US-019） Then A の通知一覧に「『タスク名』の期限は明日です」が 1 件追加される
  - Given A が担当で完了扱いでない、期限が今日で、その期限についてまだ通知していないタスク（前日にサーバーが止まっていた、例: 月曜期限で日曜は停止） When 日次処理が動く Then 「『タスク名』の期限は今日です」が 1 件追加される（Q-09-14 のサーバー停止への対応。境界値）
  - Given 同じ期限について既に通知済み When 次の日次処理が動く Then 重複して作らない（境界値: 前日に「明日です」を出したタスクに当日「今日です」は出さない）
  - Given 期限の通知が作られた後に期限が変更された When 新しい期限が今日または明日になった日の日次処理が動く Then 新しい期限について通知が作られる
  - Given 期限を過去の日に設定して保存した When 日次処理が動く Then 期限の通知は作られない（期限超過の強調表示 US-013 で気づく。境界値）
  - Given 期限を今日または明日に設定して保存した When 保存した瞬間 Then 通知はまだ作られず、次の日次処理で条件を満たしていれば作られる（境界値）
  - Given タスクを新規作成するときに、作成者以外の利用者を担当者に設定した When 作成する Then 担当者に割り当て通知が作られる（境界値）
  - Given 担当者がいないタスク When 日次処理が動く Then 期限の通知は作られない（境界値）
  - Given 画面のどこにいても When 未読の通知がある Then ヘッダーに未読件数が表示される
  - Given 通知一覧 When 通知をクリックする Then 既読になり、対象タスクの詳細画面へ遷移する
  - Given 対象タスクがゴミ箱にある When 通知をクリックする Then 「このタスクは削除されています」と表示する（異常系）
- FR-008: システムはメール・チャットなど外部への通知送信を行ってはならない（Q-03-15・Q-05-1）。

### 5.9 変更履歴・書き出し

### US-017: タスクの変更履歴を見る

- 優先度: Should
- ストーリー: リーダーとして、誰がいつ状態や担当を変えたかをたどりたい。なぜなら、状態遷移に制約を付けない代わりに履歴で経緯を追うからだ（Q-03-24・Q-03-14）。
- 受け入れ条件:
  - Given タスクの状態・担当者が変更された、またはロックが強制解除された When タスク詳細の「変更履歴」を開く Then 日時・操作者・変更前・変更後が新しい順に表示される
  - Given 上記以外の項目（タイトル・期限・メモ等）だけが変更された When 変更履歴を開く Then 履歴は追加されていない（境界値。記録対象は 3 種類に限る）
  - Given 変更が 1 件も無いタスク When 変更履歴を開く Then 「変更履歴はありません」と表示する（境界値）

### US-018: タスク一覧を CSV で書き出す

- 優先度: Should（メモ本文を含めた書き出しは Could）
- ストーリー: 利用者として、タスクの一覧を CSV で書き出したい。なぜなら、将来ほかの道具へ移るときや手元で集計するときにデータを取り出せるようにしたいからだ（Q-03-30）。
- 受け入れ条件:
  - Given 一覧画面 When 「CSV 書き出し」を押す Then 現在の絞り込み条件に合うタスクが、プロジェクト・親タスク・タイトル・状態・担当者・開始日・期限・優先度の列で、Excel で文字化けしない形式（UTF-8 BOM 付き）の CSV としてダウンロードされる
  - Given タイトルにカンマ・改行・ダブルクォートを含むタスク When 書き出す Then CSV の規則どおりにエスケープされる（異常系）
  - Given タイトルが `=` `+` `-` `@` で始まるタスク When 書き出す Then 表計算ソフトで数式として実行されない形で出力される（異常系。CSV インジェクション対策）
  - （Could）Given 「メモも含める」をオン When 書き出す Then メモ本文の列が加わる

### 5.10 利用者側の運用作業（サーバー運用者がサーバーで行う）

### US-019: セットアップスクリプトで初期導入する

- 優先度: Must
- ストーリー: サーバー運用者として、社内サーバーにコマンド 1 つでアプリを導入したい。なぜなら、手順書を読みながらの手作業は間違えやすいからだ（Q-10-1）。
- 受け入れ条件:
  - Given 前提ソフトが揃い、社内ホスト名の登録と自己署名証明書の作成（人手。environment.md）が済んだ社内サーバー（Windows 11。Q-09-12。インターネットに接続できる。Q-09-13）。前提ソフト（実行環境。人が先に入れる。一覧は設計で決定）が入っていれば、依存パッケージはスクリプトがネットから取得する When セットアップスクリプトを実行し、管理者のログイン ID と初期パスワードを入力する Then データベースが初期化され、初期状態（US-015）と管理者利用者が作られ、アプリが起動して、証明書を信頼設定した社内 LAN の他の PC から HTTPS で開ける
  - Given セットアップ済みのサーバー When Windows を起動・再起動する（毎朝の電源投入、Windows Update 後の再起動を含む） Then 人がログオンしなくてもアプリが自動で起動する（Windows のサービスとして登録する。サーバーは平日の日中だけ動く＝Q-09-14）
  - Given 最後に日次処理を行った日付と今日の日付が違う When アプリがそれを検知する（アプリ起動時・休止/スリープからの復帰時・動作中の一定間隔の確認のいずれか。検知の間隔は設計で決定） Then 日次処理（バックアップ US-020・ゴミ箱の完全削除 US-008・期限の通知 US-016・古いログの削除 NFR-008）を 1 回実行する（夜間にサーバーが止まっていても毎日 1 回は必ず動く）
  - Given 高速スタートアップが有効な Windows 11 When 終業時にシャットダウンし、翌朝に電源を入れる Then その日の日次処理が動く（異常系。高速スタートアップはサービスを再起動しないため、「起動時」だけを契機にしない。A-019）
  - Given 同じ日に 2 回目の起動をした（昼に再起動した等） When アプリが起動する Then 日次処理は再実行しない（境界値。ただしその日のバックアップが失敗していた場合は再試行する）
  - Given 土日などサーバーが丸 1 日以上止まっていた When 次に起動する Then 止まっていた日数ぶんを繰り返さず、日次処理を 1 回だけ実行する（境界値）
  - Given 既にデータベースが存在するサーバー When セットアップスクリプトを再実行する Then 既存データを上書きせずに中止し、「既に導入済みです。更新は更新スクリプトを使ってください」と表示する（異常系）
  - Given 前提ソフト（人が入れる実行環境）が足りない When 実行する Then 何が足りないかを表示して中止する（異常系）
  - Given 依存パッケージの取得中にネットワークが切れた When 実行する Then 取得できなかったものを表示して中止し、再実行で続きからやり直せる（異常系）

### US-020: データを毎日自動でバックアップし、スクリプトで復旧する

- 優先度: Must
- ストーリー: サーバー運用者として、データを毎日自動で別サーバーへ暗号化して退避し、障害時にはスクリプトで戻したい。なぜなら、サーバーが壊れたときにデータを失うと取り返しがつかないからだ（Q-10-3〜Q-10-6・P3）。
- 受け入れ条件:
  - Given 導入済みのサーバー When その日の日次処理が動く（その日最初のアプリ起動時。US-019） Then データベースのバックアップが暗号化され、社内の別サーバーのバックアップ用共有フォルダへ保存される（Q-10-5。起動直後に取るので、前回サーバーを動かした日の終業時点までの入力がすべて含まれる。RPO は NFR-004）
  - Given バックアップの実行中 When 利用者が操作する Then 操作は止まらずに続けられる（バックアップは利用中にも整合の取れた状態で取る。方式は設計で決定）
  - Given その日のバックアップが失敗した（退避先がまだ起動していない、ネットワークの準備前など） When アプリが動いている Then 当日中は一定間隔で再試行し、成功した時点で世代を回す（異常系）
  - Given 共有フォルダへの退避が 3 稼働日続けて失敗している When 管理者がログインする Then 画面に「バックアップが n 日失敗しています」の警告を出す（外部へのアラートではなく画面内の表示。Q-04-11 の範囲内）
  - Given バックアップが 7 世代ある When 新しいバックアップが成功する Then 最も古い 1 世代が削除される（Q-10-6。境界値: 失敗したときは古い世代を消さない）
  - Given 共有フォルダに接続できない When バックアップが実行される Then 失敗をエラーログに記録し、既存の世代は消さない（異常系）
  - Given 管理者 When 管理画面を開く Then 最後にバックアップが成功した日時と、直近の実行の成否が表示される（アラート通知は作らない代わりに気づく手段。Q-04-11）
  - Given サーバー運用者 When 復旧スクリプトを実行する Then バックアップの一覧から戻す世代を選び、「現在のデータは選んだ時点の内容で置き換わります」の確認に了承したときだけ復旧する（Q-10-4）
  - Given 復旧スクリプト When 復旧を実行する Then アプリを停止し、置き換える直前の現在のデータを別名で退避してから戻し、アプリを起動し直す（誤った世代を選んだときに引き返すため）
  - Given 破損した、または鍵が合わないバックアップ When 復旧を選ぶ Then 現在のデータを変更せずに中止し、理由を表示する（異常系）
  - Given 元のサーバーが壊れて使えない When 新しいサーバーでセットアップスクリプト（US-019）→ 復旧スクリプトの順に実行し、共有フォルダ上の世代と、パスワード管理ツールに保管した暗号化鍵の控え（Q-10-7）を指定する Then 元のサーバーの最新バックアップ時点のデータで使えるようになる（機材喪失からの復旧経路。セットアップ直後の空のデータは復旧で置き換わる）

### US-022: 更新スクリプトで新しい版に入れ替える

- 優先度: Must
- ストーリー: サーバー運用者として、2 回目以降の更新をコマンド 1 つで行い、データを引き継ぎたい。なぜなら、更新のたびの手作業を無くし、更新でデータが消える事故を防ぎたいからだ（Q-10-2）。
- 受け入れ条件:
  - Given 日次処理（バックアップ）の実行中 When 更新スクリプトを実行する Then 日次処理の完了を待ってから停止する（朝の更新作業と起動時バックアップの衝突。異常系）
  - Given 旧版が稼働中 When 更新スクリプトを実行する Then 停止 → バックアップ → 入れ替え → （必要なら）データベースのスキーマ変更 → 起動 の順に進み、更新前に登録したタスク・メモ・利用者・状態・履歴・ゴミ箱の内容がすべて残っている
  - Given スキーマ変更を含む版 When 更新スクリプトがスキーマ変更の段階に来る Then 適用する SQL を画面に表示し、実行者が承認したときだけ適用する（Q-09-9）
  - Given 入れ替え後に起動しない（スキーマ変更なし） When 更新スクリプトが起動確認に失敗する Then 自動で 1 つ前の版に戻して起動し、失敗を表示する（Q-09-7）
  - Given スキーマ変更を適用した後に起動確認に失敗する When 更新スクリプトが検知する Then 自動では戻さず、更新前のバックアップの場所と戻し方を表示して実行者の判断を求める（異常系。Q-09-7）
  - Given 実行者がスキーマ変更の承認を拒否する When 更新スクリプトが続きを判断する Then 旧版のまま起動し直して中止する（異常系）
  - Given スキーマ変更の SQL が適用の途中で失敗した When 更新スクリプトが検知する Then 途中まで適用された変更を取り消せる場合は取り消し、取り消せない場合はアプリを起動せずに、更新前バックアップの場所と復旧スクリプトでの戻し方を表示して止まる（異常系。自動で旧版を起動しない＝データ構造と版の不一致を防ぐ）

### US-021: ドラッグ＆ドロップで操作する

- 優先度: Could
- ストーリー: 利用者として、一覧の階層やカレンダーの日付をドラッグで動かしたい。なぜなら、メニュー操作より速いからだ（Q-03-4・Q-03-6・Q-03-28）。
- 受け入れ条件:
  - Given 一覧 When 編集権限のあるタスクを別の親の上へドラッグする Then US-007 と同じ規則（自分の配下への移動は拒否・ロック中は拒否）で移動する（異常系を含む）
  - Given カレンダー When 編集権限のあるタスクの帯を別の日へドラッグする Then 開始日と期限が同じ日数だけずれる。他人がロック中なら拒否する（異常系）
- 優先度の決め方: カレンダーの日付ドラッグは Q-03-6 の仮回答では Should、Q-03-28 の仮回答では「ドラッグ操作」として Could。カレンダー自体が Should のため、Q-03-28 に合わせて Could とした（A-005）。

### 5.12 優先度の導出（Q-03-28 に無い項目）

Q-03-28 で Must と明示されたのは「階層タスクの登録・一覧・編集、ログイン、ロック、メモ」、Should は「カレンダー表示、状態のワークフロー定義、通知」、Could は「ドラッグ操作、全文検索」。それ以外の US の優先度は作成者が次の理由で導いた（A-011。ゲートで確認する）。

| US | 優先度 | 導出の理由 |
|---|---|---|
| US-002・US-003 | Must | ログイン（Must）は利用者の登録と初期パスワードの変更が無いと成り立たない |
| US-007 | Must | Q-03-28「階層タスクの編集」に階層の組み替えを含めた。ただし「手動順」の上へ・下へ（A-004）は確認対象 |
| US-008 | Must | Q-03-23（必須・高影響）で削除の取り消しが求められ、削除のできない編集は実用にならない |
| US-011 | Must | Q-03-28「ロック」に含めた。強制解除が無いとロックの握りっぱなしで 30 分作業が止まる（P2） |
| US-012・US-013 | Must | Q-03-28「一覧」と、Q-01-2「誰が・いつまでに・どこまでが 1 画面で見える」・成功指標 3 に直結する |
| US-017 | Should | 記録（US-011）は Must、閲覧画面は Q-03-24 の優先度が未指定のため Should |
| US-018 | Should | Q-03-30 は将来の移行用で、初回利用には不要 |
| US-019・US-020・US-022 | Must | 社内サーバーで複数人が使う以上、導入・データ保全・更新でのデータ引き継ぎが無いと運用を始められない（Q-10-1〜Q-10-4 はすべて必須回答） |

Must は 22 件中 16 件で多い。Q-06-1「数週間以内に一度触りたい」に対して重い場合は、US-012 の絞り込みの一部・US-013 の件数表示・US-022（初回リリース時点では更新が発生しない）を Should に下げる余地がある（ゲートで確認する）。

## 6. 制約条件

- 納期・予算・既存システム連携・法規制・社内ポリシーなど:
  - 納期: 明確な締切は無い。動くもの（Must の範囲）を数週間以内に一度触りたい（Q-06-1）。
  - 費用: 運用費は月 0 円。自宅・社内にある既存の機材だけを使い、有料の外部サービスを使わない（Q-06-2。NFR-012）。
  - 実行環境: 社内のオンプレミスサーバー 1 台で動かし、社内 LAN からだけアクセスする（Q-09-1・Q-09-2。environment.md）。
  - データベース: 別のデータベースサーバーは立てず、アプリと一緒に動く軽いものにする（memo.md 22 行目「簡易」・Q-06-4）。製品の選定は設計フェーズで行う。
  - 技術: 必須・禁止の技術指定は無く、選定は設計フェーズに任せる（Q-06-3）。
  - 既存システム連携・データ移行: 無し（Q-06-3）。
  - 機密性: 社外秘・機密を含む可能性があり、データを社外へ送らない（Q-04-4。NFR-006・NFR-013）。
  - 開発体制: 1 人開発（Q-09-8「1 人開発のうちは」）。
