## リポジトリ側セキュリティ設定チェックリスト

エージェントは実行ツール（Bash 等）経由でファイル書き込み・git 操作ができるため、
ハーネスのフック（提案層）だけでは防げない操作がある。リポジトリ側の強制層で
塞げるものは、要件定義の時点で有効化を確認しておく（GitHub 以外のホスティングでは
相当機能の有無を確認し、無ければ「なし」と理由を記録する）。

| 設定 | 目的 | 確認 |
|---|---|---|
| Secret scanning + push protection | シークレットを含む push をサーバー側で拒否する（Bash 書き込み穴を強制層で塞ぐ唯一の手段） | [ ] |
| CodeQL（default setup） | push / PR ごとの静的解析 | [ ] |
| Dependabot（alerts + security updates） | 依存脆弱性の検知と更新 PR | [ ] |
| ブランチ保護 + CODEOWNERS | 保護ブランチへの直接 push 禁止・重要パスのレビュー必須化 | [ ] |
| （クライアント側）security-guidance プラグイン | 実装中の差分レベルのセキュリティ助言（本ハーネスの release-security-review スキルはリリースゲート統合専用で、検出はビルトイン層が正） | [ ] |
| claude-code-security-review Action の採否 | PR ごとの自動セキュリティレビュー（`.github/workflows/` の `.example`。API 費用がかかるため採否を理由つきで判断・記録する） | [ ] |

## 自動化できる/できない境界

エージェントが実際にリリースを自動実行するにあたり、**どこまでを自動化してよいか**を明確にする。

| 作業 | 自動化可否 | 理由・人手が必要な場合の担当 |
|---|---|---|
| ビルド・パッケージング | 自動 | |
| テスト実行 | 自動 | |
| デプロイ（インフラへの反映） | 自動 / 人手 | 例: 支払い情報の入力、外部ダッシュボードでの手動承認、ドメイン購入は人手 |
| DBマイグレーション | 自動 / 人手 | |
| 監視・アラート設定 | 自動 / 人手 | |
| 本番切り替え（カットオーバー） | 自動 / 人手 | |

「人手」に分類した項目は、リリースエージェントが該当ステップで作業内容を提示し、
ユーザーに実行してもらってから先に進む。

**「自動」の意味（承認の規範は AGENTS.md が正）**: 「自動」は「エージェントが準備（ビルド・
パッケージング・dry-run / plan・ローカル検証・チェックリスト作成）まで確認なしに進めてよい」
という意味であり、**外部反映（push・タグ付け・デプロイ・公開・公開 API の書込）そのものは
分類に関わらず必ずユーザーの exact-action 承認（何を・どこへ・どの引数）を経る**。承認の単位は
`docs/05-release/release-checklist.md` の action packet の行で、フック（guard-dangerous-git /
guard-external-effect）が実行時にも同じ単位で確認を入れる。「自動」に分類したからといって
承認が省略されることはない。

上の表は開発・リリース作業の境界。これとは別に、**利用者側の運用作業**に
どこまで手作業を残してよいかを確認する（**「手順書に書く」は自動化の代替ではない**。
この方針が不明のまま進み、リリース直前に「すべて自動にする」方針が判明して
