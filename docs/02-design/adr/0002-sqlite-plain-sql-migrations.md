# ADR 0002: データストアに SQLite（WAL）を使い、スキーマ変更は番号付きの素の SQL ファイルで管理する

- 日付: 2026-09-26
- ステータス: 承認済み

## コンテキスト

- 別のデータベースサーバーは立てず、アプリと一緒に動く軽いものにする（Q-06-4）。規模は同時 10 人・3 年で 15,000 件（NFR-010）。
- スキーマ変更は、更新スクリプトが**適用する SQL を画面に表示し、実行者が承認したときだけ**適用する（Q-09-9・US-022）。途中で失敗したら取り消せるものは取り消す。
- 利用中でも整合の取れたバックアップを取る（US-020）。

## 検討した選択肢

| 選択肢 | メリット | デメリット |
|---|---|---|
| A. SQLite + Dapper + 番号付き SQL ファイル（`migrations/NNNN_*.sql`） | 表示する SQL と実行する SQL が同一ファイルなので、承認の対象が明確。SQLite は DDL もトランザクションに入るため、1 ファイルを 1 トランザクションで適用すれば途中失敗を丸ごと取り消せる。SQLite のオンラインバックアップ API で利用中に一貫したコピーが取れる | SQL とマッピングを手で書く |
| B. SQLite + EF Core Migrations | モデルからマイグレーションを生成できる | 実行時に生成される SQL を事前に表示するには `migrations script` を別途出力する必要があり、承認した SQL と実際に流れる SQL が一致する保証を別に作る必要がある。SQLite では多くのテーブル変更がテーブル再作成になり、生成 SQL が読みにくい |
| C. LiteDB 等の組込み NoSQL | スキーマ変更が不要 | 「SQL を提示して承認」（Q-09-9）の要件と噛み合わない。階層の再帰問い合わせを自前で書く |

## 決定

A を採用する。

- 接続は `Microsoft.Data.Sqlite`、マッピングは Dapper。`PRAGMA journal_mode=WAL`・`foreign_keys=ON`・`busy_timeout=5000`。
- スキーマの版は `schema_version` テーブルで管理し、配布物の `migrations/` にある未適用のファイルを番号順に適用する。**各ファイルは 1 トランザクションで適用し、失敗したらそのファイル分をロールバックする。** 複数ファイルのうち先行分が成功して後続が失敗した場合は「取り消せない」側に倒し、US-022 の「起動せずに更新前バックアップの場所を表示して止まる」経路に入る。
- アプリ本体は起動時にスキーマの版を確認し、**配布物が期待する版と DB の版が一致しなければ起動を拒否する**（自分でマイグレーションしない。承認を経ない適用を防ぐ）。
- 階層は隣接リスト（`parent_task_id`）で持ち、祖先・子孫は再帰 CTE で辿る。15,000 件なら一覧はメモリ上でツリーを組めば十分速い（NFR-001。性能は architecture.md §6）。
- 文字列比較用に、タイトルを NFKC 正規化＋小文字化した `title_norm` 列を持つ（検索の仕様は architecture.md §9）。

## 結果・影響

- 捨てたもの: ORM による型安全なクエリ生成。SQL は Repository 層に閉じ込め、結合テストで実 SQLite に対して検証する。
- 同時書き込みは SQLite の単一ライターで直列化される。10 人規模の保存操作（500ms 以内。NFR-001）なら待ちは数 ms で問題にならない。規模が大きく変わったら（A-006 の見直し時）移行を再検討する。
- 失敗モード: DB ファイルのロック競合（`SQLITE_BUSY`）は `busy_timeout` で待ち、超えたらエラー ID `E-DB-BUSY` の画面を出す（再操作を促す）。影響はその 1 リクエストに閉じる。
