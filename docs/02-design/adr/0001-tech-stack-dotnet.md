# ADR 0001: 技術スタックに .NET 10（ASP.NET Core Razor Pages）を採用する

- 日付: 2026-09-26
- ステータス: 承認済み（2026-09-26 ユーザーが「.NET」を選択。版の選定はこの ADR で行う）

## コンテキスト

- サーバーは社内の Windows 11 マシン 1 台で、平日の日中だけ電源が入る（environment.md・Q-09-12・Q-09-14）。
- 初期導入・更新・復旧をスクリプト 1 つで行い、更新失敗時は自動で 1 つ前の版に戻す（US-019・US-020・US-022・Q-09-7）。
- Windows のサービスとして自動起動する（US-019）。運用費は月 0 円（NFR-012）、1 人開発で数週間以内に Must の範囲を動かしたい（Q-06-1）。
- 画面は PC ブラウザが主で、スマートフォンは閲覧だけ（NFR-011）。外部 CDN を読み込まない（NFR-006 (4)）。

## 検討した選択肢

| 選択肢 | メリット | デメリット |
|---|---|---|
| A. .NET 10 + ASP.NET Core Razor Pages + SQLite | Windows サービスに標準対応（`Microsoft.Extensions.Hosting.WindowsServices`）。self-contained 発行で単一フォルダを配布でき、サーバーに前提ソフトが要らない。フォルダの入れ替えだけで更新・ロールバックできる。CSRF 対策・Cookie 認証・パスワードハッシュが標準で揃う | 画面の対話的な部分（ツリー展開・自動保存・プレビュー）は素の JavaScript で書く必要がある |
| B. Node.js/TypeScript + Hono + React/Vite + SQLite | 画面の作り込みが速い | サーバーに Node の導入が要る（前提ソフトが増える）。サービス化に WinSW 等の追加ツールが要る。node_modules を配布物に同梱し、ネイティブモジュール（SQLite）の Windows ビルドを管理する必要がある |
| C. Python + FastAPI + Jinja/htmx + SQLite | 記述量が少ない | サーバーに Python と仮想環境が要る。更新時の依存の再取得がネットワーク障害に弱い（US-019 の異常系が重くなる）。サービス化に追加ツールが要る |

## 決定

A を採用する。版は **.NET 10（LTS。サポート期限 2028-11）**。ユーザーの選択肢の表記は「.NET 8」だったが、.NET 8 は 2026-11 にサポートが終わる。本番投入の直後に期限を迎えるため、同じ系列の現行 LTS に上げた（API の違いは設計に影響しない）。

- 画面はサーバー側で描画する（Razor Pages）。対話的な部分だけ、リポジトリに同梱した素の JavaScript（ES Modules）で補う。フロントエンドのビルド工程（npm 等）は持たない。
- 発行は `dotnet publish -c Release -r win-x64 --self-contained true` とする。配布物は ZIP 1 つで、実行に .NET ランタイムの導入は要らない。

## 結果・影響

- US-019 の「前提ソフト」は **Windows 11 と標準の Windows PowerShell 5.1 だけ**になる。「依存パッケージ」は CI のビルド時に NuGet から取得して配布物に同梱するため、サーバー上のセットアップスクリプトはネットワークから何も取得しない。US-019 の「取得中にネットワークが切れた」異常系は、人が GitHub から配布物 ZIP を取得する段階へ移る。セットアップスクリプトは ZIP の SHA-256 を配布物に同梱のチェックサムと照合し、不一致なら中止する。
- 捨てたもの: SPA 型の滑らかな画面遷移。ドラッグ＆ドロップ（US-021・Could）は素の JavaScript で後から足す。
- 将来の変更: 画面の一部を SPA にしたくなっても、API エンドポイント（architecture.md §5）は JSON で切ってあるので、画面単位で差し替えられる。
- **新しい失敗モード（常駐プロセス）の受け皿**: このプロジェクトで初めての常駐プロセスになる。
  - フォールバック表示: 起動に失敗したときはブラウザから接続できない。利用者は管理者に伝える（NFR-008 (3)。自動のアラート通知は作らない）。
  - エラー境界: 起動時の例外はホストの最上位で捕まえ、ログファイル（NFR-008）と Windows イベントログに書いてから終了コード 1 で終わる。リクエスト処理中の例外は ASP.NET Core の例外ハンドラで捕まえ、エラー画面（エラー ID 付き）を返す。日次処理（BackgroundService）の例外はジョブの中で捕まえてログに書き、プロセスを落とさない。
  - リトライ: Windows サービスの回復設定で、異常終了したら 1 分後に再起動する（1 回目・2 回目。3 回目以降は再起動しない）。更新スクリプトの起動確認はヘルスチェック URL（`/healthz`）で行う（US-022）。
  - 影響範囲: 日次処理の失敗は日次処理だけに閉じ込める（画面は使い続けられる）。起動失敗はアプリ全体が止まるが、データは SQLite ファイルに残り、復旧スクリプトで戻せる。
