# ADR 0005: 日次処理は「最後に実行した日付」との比較で起動し、バックアップは SQLite オンラインバックアップ＋AES-256-GCM で退避する

- 日付: 2026-09-26
- ステータス: 承認済み

## コンテキスト

- サーバーは平日の日中だけ動く。高速スタートアップではサービスが再起動しないため、「起動時」だけを契機にできない（US-019・A-019）。
- 日次処理（バックアップ・ゴミ箱の完全削除・期限の通知・古いログの削除）は 1 日 1 回、止まっていた日数ぶんは繰り返さない。その日のバックアップが失敗していれば当日中に再試行する（US-019・US-020）。
- バックアップは利用中に整合の取れた状態で取り、暗号化して社内の別サーバーの共有フォルダへ 7 世代置く（US-020・NFR-009）。退避先の起動が遅い場合がある（A-022）。

## 検討した選択肢

| 選択肢 | メリット | デメリット |
|---|---|---|
| A. アプリ内の BackgroundService が 5 分ごとに「`daily_runs` の最終日付 ≠ 今日（日本時間）」を確認 | 起動・休止からの復帰・日付変更のどれでも 5 分以内に拾える。OS のタスクスケジューラに依存しない | 5 分の遅れがある |
| B. Windows タスクスケジューラで起動時・毎日に実行 | OS の標準機能 | 高速スタートアップの「起動」を拾えない（A-019）。スクリプトとアプリの二重管理になる |
| バックアップ方式 A. SQLite オンラインバックアップ API（`SqliteConnection.BackupDatabase`）→ 一時ファイル → 暗号化 → 共有フォルダ | WAL 下でも書き込みを止めずに一貫したスナップショットが取れる | 一時ファイル分のディスクを使う（数十 MB 程度） |
| バックアップ方式 B. DB ファイルを直接コピー | 単純 | WAL 中のコピーは不整合になりうる |

## 決定

日次処理は A、バックアップは方式 A を採用する。

- **日次処理の契機**: `DailyJobService` が起動直後と以後 5 分ごとに、`daily_runs` テーブルの最終実行日（日本時間の暦日）を今日と比べる。違えば日次処理を 1 回実行し、今日の日付を記録する。止まっていた日数は問わない（1 回だけ）。
- **日次処理の中身と順序**: (1) バックアップ → (2) 期限切れロックの掃除 → (3) ゴミ箱の完全削除（30 日超） → (4) 期限の通知（US-016・A-020 (a)） → (5) 90 日超のログの削除。(2)〜(5) はそれぞれ独立に try/catch し、失敗しても他を止めない。
- **バックアップの再試行**: その日のバックアップが失敗していたら、同じ日のうちは **30 分ごと**に再試行する（US-020。§5.13 の決定事項）。日付の記録は (2)〜(5) の完了で行い、バックアップの成否は `backup_runs` に別に記録する（同日 2 回目の起動で (2)〜(5) を再実行しない・バックアップだけ再試行する＝US-019）。
- **暗号化**: AES-256-GCM。1 MiB ごとのチャンクに分け、各チャンクに固有の nonce と認証タグを付ける（ファイル先頭にマジック・版・ソルトを置く）。鍵は 32 バイトの乱数で、セットアップ時に生成してサーバー上には DPAPI（LocalMachine スコープ）で保護し、実行アカウントと Administrators だけが読める ACL のファイルに置く。控えは Base64 で 1 回だけ画面に表示し、人がパスワード管理ツールに保管する（Q-10-7）。
- **退避先への書き込み**: UNC パスへ `名前.tmp` で書き、書き終えたら改名する（途中で切れた世代を残さない）。共有フォルダの資格情報は、セットアップ時に人が入力し、DPAPI で保護して同じ ACL のファイルに置く。書き込みの前に `WNetAddConnection2` で接続する。
- **世代管理**: 成功した後にだけ、最も古い世代を消して 7 世代にする。失敗時は消さない（US-020）。更新スクリプトの直前バックアップは `pre-update/` に別に置き、世代に数えない（NFR-009）。
- **警告**: `backup_runs` を見て、成功が 3 稼働日（バックアップを試みた日）続けて無ければ、管理者のヘッダーに警告を出す（US-020）。

## 結果・影響

- 5 分以内の遅れで日次処理が走るため、朝の電源投入直後の最初の数分はバックアップ前の状態で使われる。RPO の定義（A-021）には影響しない。
- 更新スクリプトとの衝突: 日次処理の実行中は `daily.lock` ファイルを持ち、更新スクリプトはこれが消えるまで待つ（US-022）。
- **新しい失敗モード（バックグラウンド処理・外部の共有フォルダ依存）の受け皿**:
  - フォールバック表示: 管理画面の「最後に成功した日時・直近の成否」と、3 稼働日連続失敗の警告（US-020）。
  - エラー境界: 日次処理の各ステップの try/catch。例外はログに書き、画面の処理には波及させない。
  - リトライ: バックアップだけ当日中 30 分ごと。他のステップは翌日に持ち越す（冪等に書く）。
  - 影響範囲: 日次処理に閉じ込める。共有フォルダに届かなくても画面は使える。
- 捨てたもの: 増分バックアップ。数十 MB 規模なので毎回フルでよい。
