# ADR 0006: 配布は GitHub Release の ZIP、サーバーでは Windows サービス＋PowerShell スクリプトで導入・更新・復旧し、TLS は社内ルート CA で発行する

- 日付: 2026-09-26
- ステータス: 承認済み

## コンテキスト

- GitHub Actions から社内サーバーには届かない。サーバー上で人が配布物を取得してスクリプトを実行する（environment.md）。
- 導入・更新・復旧は 1 コマンド。更新は停止 → バックアップ → 入れ替え → （承認制の）スキーマ変更 → 起動。スキーマ変更なしで起動に失敗したら自動で 1 つ前の版に戻す（US-019・US-020・US-022）。
- HTTPS は自己署名証明書。PC とスマートフォンに信頼設定を入れる（人手。Q-02-4・A-016）。スマートフォンは SAN 必須・有効期間の上限がある（requirements.md §5.13）。
- Windows 11 はクライアント OS で、IIS 等には同時接続数の制限がある（A-023）。

## 検討した選択肢

| 選択肢 | メリット | デメリット |
|---|---|---|
| 配布 A. GitHub Release に self-contained の ZIP（＋SHA-256）を置き、人がブラウザで取得 | サーバーに git も認証トークンも要らない。版が明確 | 取得は手作業（人手作業の範囲。environment.md と整合） |
| 配布 B. サーバーでタグを clone してビルド | 配布物を作らない | サーバーに .NET SDK と git と GitHub の認証が要る |
| Web サーバー A. Kestrel を直接 443/80 で待ち受け | IIS を使わないので構成が単純で、IIS の同時接続制限の対象外 | 証明書の読み込みを自分で設定する |
| Web サーバー B. IIS の背後に置く | 定番 | Windows 11 の IIS は同時接続数の制限を受ける。設定が増える |
| 証明書 A. 自己署名のサーバー証明書を直接信頼させる | 手順が 1 段 | 更新のたびに全端末で信頼設定をやり直す |
| 証明書 B. 社内用ルート CA（10 年）を作って端末に 1 回だけ信頼させ、サーバー証明書（397 日）をそれで発行する | 証明書を更新しても端末の設定をやり直さない。397 日は iOS・Chrome の上限（398 日）に収まる | 手順が 1 段増える。ルート CA の秘密鍵を安全に保管する必要がある |

## 決定

配布 A・Web サーバー A・証明書 B を採用する。

- **配置**（サーバー上）:
  - `C:\TodoApp\releases\<版>\` … 展開した配布物（直近 2 版を残す）
  - `C:\TodoApp\current` … 稼働中の版へのジャンクション。サービスはここの exe を起動する
  - `C:\TodoApp\data\` … `todo.db`・`secrets\`（DPAPI で保護した鍵と資格情報）・`logs\`。ACL は実行アカウントと Administrators だけ
  - `C:\TodoApp\certs\` … サーバー証明書（PFX）
- **サービス**: 名前 `TodoApp`。実行アカウントは仮想アカウント `NT SERVICE\TodoApp`。スタートアップは自動（遅延開始）。回復設定は 1 回目・2 回目に 1 分後に再起動。登録は `sc.exe` で行う。
- **待ち受け**: 443（HTTPS）と 80（HTTPS へ 301 転送。NFR-006）。Windows Defender ファイアウォールの受信規則（プライベートプロファイル・TCP 80/443）は**セットアップスクリプトが作る**（A-023 の「スクリプトか人手か」の決定）。ネットワークプロファイルを「プライベート」にするのは人手のままにする（環境全体に効くため）。
- **スクリプト**（配布物の `scripts\` に同梱。Windows PowerShell 5.1 で動く。管理者権限で実行）:
  - `Install-TodoApp.ps1`（US-019）: 前提確認（OS・管理者権限・443/80 の空き・証明書ファイル）→ データフォルダと ACL → 鍵の生成と控えの表示 → 共有フォルダの資格情報の入力 → `TodoApp.exe migrate --init` → 管理者利用者の作成 → サービス登録 → ファイアウォール規則 → 起動 → `/healthz` の確認。`todo.db` が既にあれば何もせず中止する。
  - `Update-TodoApp.ps1`（US-022）: `daily.lock` を待つ → サービス停止 → `pre-update\` へバックアップ → 新版を展開 → `TodoApp.exe migrate --plan` で未適用 SQL を表示 → 承認されたら `migrate --apply`（拒否なら旧版で起動して中止）→ `current` を切り替えて起動 → `/healthz` を 60 秒待つ。スキーマ変更が無く起動に失敗したら `current` を旧版に戻して起動する。スキーマ変更後の失敗・適用途中の失敗では起動せず、バックアップの場所と `Restore-TodoApp.ps1` の使い方を表示して止まる。
  - `Restore-TodoApp.ps1`（US-020）: 世代の一覧から選択 → 確認 → サービス停止 → 復号と整合性検査（GCM のタグ・`PRAGMA integrity_check`）を**一時ファイルで先に行う** → 現在の `todo.db` を `todo.db.before-restore-<日時>` に退避 → 置き換え → 起動。鍵を持たない新サーバーでは、パスワード管理ツールの控えの入力を求める。
  - `New-TodoAppCertificate.ps1`（人が実行する補助）: ルート CA の作成（初回だけ）とサーバー証明書の発行（SAN にホスト名と IP アドレス）。ルート CA の秘密鍵は PFX にしてパスワードをかけ、サーバーには残さない（パスワード管理ツールと同じ場所に保管するよう表示する）。
- **CI**（GitHub Actions）: push・PR では `ubuntu-latest` でビルドと全テスト（.NET はクロスプラットフォーム）と gitleaks によるシークレット検出。タグ `v*` の push でのみ `windows-latest` で発行・ZIP 化・PowerShell スクリプトのテスト（Pester）を行い、Release に ZIP と SHA-256 を添付する（Windows ランナーの消費を最小にする。A-024）。

## 結果・影響

- サーバーに必要な前提は Windows 11・PowerShell 5.1・管理者権限のアカウントだけになる（US-019 の前提ソフト一覧）。
- 捨てたもの: 自動デプロイ（CD）。environment.md のとおり人手とする。
- Windows 11 の使用許諾上の同時接続数（A-023）は、IIS を使わないことで技術的な制限は避けられるが、使用許諾条項の解釈は人が確認する必要がある（リスクとして残す）。
- 証明書の期限切れ: 要件どおり、期限の日付をリリース時に `docs/05-release/` に記録して人が更新時期を管理する（environment.md）。アプリに期限の警告は持たせない（要件に無い）。
