### トークン効率（effort-report.md を見ながら）

`python tools/effort-report.py` で `docs/06-retrospective/effort-report.md` を
`.github/hooks/logs/usage/` の受領書から生成・更新してから、次の3点を確認する
（自動記録は Claude Code セッションのみ。旧 effort-log.csv は `--migrate` で取り込む）。

- **モデルは適切だったか**: 機械的な作業（task-worker 等）に高価なモデルを
  使っていないか。逆に設計・レビューを安いモデルで行って手戻りが出ていないか。
- **無駄なトークンはないか**: 差し戻しの往復、同一工程のセッション数過多、
  cache_read が極端に大きいセッション（長すぎる会話 = context rot 帯域）の兆候。
- **上流品質との相関**: 差し戻し1往復で消えたトークンと spec-critic 1回の
  トークンを比較する（独立レビューの費用対効果の実測）。

## 4.5 引き算の点検（de-scaffolding と learnings 棚卸し）

ハーネスの各要素は「モデル/環境が単独でできないこと」の仮定をエンコードしており、
モデルの向上でその仮定は陳腐化する。**足りないガードだけでなく、不要になったガードも問う**。

- **不要になったガード・手順はないか**: 今回、一度も価値を発揮しなかった確認・手順・
  ガードはどれか（発火0回のフック・形骸化したチェックリスト項目）。それは
  「たまたま出番が無かった」のか「もうモデルが単独でできる」のか。
  後者なら削除・簡素化を改善提案に含める（複雑さ自体がコストであり事故原因になる）。
- **learnings.md の棚卸し**: 失効した教訓（環境が変わって当てはまらない・ハーネス側で
  機械化済み）を削除し、繰り返し効いている教訓はスキルへの昇格を検討する
  （learnings は SessionStart で毎回注入されるため、死んだ行はコンテキストの無駄になる）。
